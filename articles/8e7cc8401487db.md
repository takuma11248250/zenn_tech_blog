## テストを書き始める前に、何が漏れているか

データ基盤を運用していると、「このテーブルにテストを追加しておいて」という依頼をよく受けます。

そこでよくあるのが、`not_null`や`unique`をとりあえず主要なカラムに貼っていく進め方です。テストが並んでいると一見網羅できているように見えますが、実際に事故が起きるのは、そもそも「そのテストを書く」という発想すら浮かばなかった観点からです。

**テストの実装から入ると、書きやすいテストばかりが増えて、守るべきものが漏れる。**この順番を逆にするだけで、テスト設計の質はかなり変わります。

## データ品質には5つの観点がある

先にやるべきことは、対象のデータに対して「守るべき品質」を観点ごとに洗い出すことです。データ品質には、大きく次の5つの観点があります。

| 観点 | 意味 |
| --- | --- |
| 正確性(Accuracy) | 値が実態・ルールと合っているか |
| 完全性(Completeness) | 必要な値が欠けていないか |
| 一貫性(Consistency) | 他のデータと矛盾していないか |
| 適時性(Timeliness) | データが十分新しいか |
| 一意性(Uniqueness) | 重複していないか |

たとえば注文データであれば、次のように当てはめられます。

- 正確性: 注文ステータスが決められた値のいずれかになっているか
- 完全性: 金額(amount)が入力されているか
- 一貫性: 注文の顧客IDが、実在する顧客を指しているか
- 適時性: 最新の注文データがどれだけ前のものか
- 一意性: 注文IDが重複していないか

この5つを先に並べてから、「今回のデータでは、どの観点が特に危ないか」を考えます。決済が絡むテーブルなら正確性と一貫性、日次バッチで集計するテーブルなら適時性、といった具合に、対象データの性質によって優先度は変わります。**この優先度づけをテスト実装の前にやっておくかどうかが、後から「あのカラム、テストしてなかったんですか」と言われるかどうかの分かれ目**です。

## 観点が決まれば、テスト手法は機械的に決まる

観点を洗い出せてしまえば、あとはそれぞれに対応するテスト手法を当てはめるだけです。個人開発で作っているデータエンジニア向け学習教材[de-quest](https://de-quest.com/)でも、同じ順番でハンズオンを組んでいます。ここでは、その教材で使っている注文データの例をもとに説明します。

わざと3種類の品質問題を仕込んだ、次のようなデータがあるとします。

```csv
id,customer_id,status,amount,order_date
1,1,shipped,4500,2026-08-01
2,1,pending,3000,2026-08-10
3,2,cancelled,1200,2026-08-05
4,3,shipped,,2026-08-15
5,4,unknown_status,900,2026-08-20
```

4件目は`amount`が空(完全性の問題)、5件目は`unknown_status`という想定外のステータス(正確性の問題)、さらに存在しない顧客ID`4`を参照しています(一貫性の問題)。

### 完全性・一意性は、dbtの標準テストで足りる

完全性と一意性は、dbtに最初から組み込まれている`not_null`・`unique`で検出できます。

```yaml
models:
  - name: stg_orders
    columns:
      - name: order_id
        tests:
          - unique
          - not_null
      - name: amount
        tests:
          - not_null
```

列名を指定するだけで、`amount`の欠損も`order_id`の重複もそのまま検出対象になります。

### 一貫性は relationships、正確性は accepted_values

一貫性は、他のテーブルとの整合性を見る`relationships`テストで検証します。

```yaml
      - name: customer_id
        tests:
          - relationships:
              arguments:
                to: ref('stg_customers')
                field: customer_id
```

正確性は、値のパターンが決まっているなら`accepted_values`が使えます。

```yaml
      - name: status
        tests:
          - accepted_values:
              arguments:
                values: ['pending', 'shipped', 'cancelled']
```

顧客マスタに存在しない顧客ID`4`を参照する行、`unknown_status`という不正な値を持つ行が、それぞれのテストで検出されます。

### 適時性は、標準テストにない。だからカスタムSQLで書く

ここまでの4つは、dbtが標準で用意しているテストで対応できました。一方で**適時性は標準テストに存在しないため、自分でSQLを書く必要があります**。ここで観点の洗い出しをサボっていると、この項目自体が抜け落ちます。

```sql
-- tests/assert_data_is_fresh.sql
select
    max(order_date) as latest_order_date,
    date_diff('day', max(order_date), current_date) as days_since_latest
from {{ ref('stg_orders') }}
having date_diff('day', max(order_date), current_date) > 30
```

`SELECT`で行が1件でも返ればテスト失敗、というのがdbtのシンギュラーテストの基本パターンです。「最新の注文日から30日以上経過していたら失敗」という条件を`HAVING`句で表現しています。

こうして見ると、**5つの観点それぞれに「標準テストで済むもの」と「自分でSQLを書く必要があるもの」が混在している**ことが分かります。観点を先に洗い出さずにテストの実装から入っていたら、適時性はほぼ確実に抜けていたはずです。

## テストは「実行して失敗を確認する」だけでは終わらない

観点を網羅してテストを書けたとしても、それだけでは半分の仕事です。テストが失敗したときに誰かが気づく仕組みと、気づいた後に何をすべきかまでセットで設計しないと、テストは動いているだけの飾りになります。

失敗検知は、`dbt test`の終了コードを使えばシェルスクリプトで組めます。

```bash
#!/bin/bash
if dbt test; then
  echo "OK: 全テストがパスしました"
else
  echo "!!! アラート: dbtテストが失敗しました !!!"
  exit 1
fi
```

実務では`else`ブロックの中で、SlackやPagerDutyへの通知処理を書きます。**「テストの実行」と「失敗時にどう気づかせるか」は必ずセットで設計する**べきものです。

さらに、検出した問題は一覧にまとめておくと、対応の優先順位がつけやすくなります。

| 観点 | テスト | 結果 | 該当件数 | 対応 |
| --- | --- | --- | --- | --- |
| 完全性 | not_null(amount) | FAIL | 1件 | 注文ID4のamountを確認・修正依頼 |
| 一貫性 | relationships(customer_id) | FAIL | 1件 | 注文ID5の顧客ID登録漏れを調査 |
| 正確性 | accepted_values(status) | FAIL | 1件 | 注文ID5のstatus値を修正 |
| 適時性 | カスタムテスト(鮮度) | PASS | - | 直近30日以内のデータで問題なし |
| 一意性 | unique(order_id) | PASS | - | 問題なし |

失敗件数の一覧だけでは、見た人が「で、これはどうすればいいの?」となってしまいます。**「何件失敗したか」ではなく「次に誰が何をすべきか」まで書いてあるかどうか**が、レポートとして機能するかの分かれ目です。

## まとめ

- テストの実装から入ると、書きやすいテストだけが増えて、本来守るべき観点が漏れる
- **先に「正確性・完全性・一貫性・適時性・一意性」の5観点で対象データを洗い出す**ことで、抜け漏れなくテスト設計ができる
- 観点が決まれば、テスト手法は機械的に決まる。dbtの標準テスト(`not_null`/`unique`/`relationships`/`accepted_values`)で済む観点と、カスタムSQLを書く必要がある観点(適時性など)が混在することも多い
- **テストは実行して失敗を確認するだけでは意味がなく、アラートで気づく仕組みと、対応まで書いたレポートまでセットで設計する**必要がある

データ品質テストに限らず、「実装から入らず、先に守るべきものを洗い出す」という順番は、データ基盤のさまざまな設計判断で応用できる考え方だと思っています。
